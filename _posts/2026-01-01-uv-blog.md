Python packaging has never lacked tools. It has lacked consistently simple workflows. 

Pip installs pacakging, but it does not manage project environments. Python versions, lockfiles, or command-line tools. Over time, developers combined it with venv, pyvenv, pip-tools, pipx, Poetru, or Conda. Each tool solved a real problem, but the resulting workflow requiered developers to remember which tool owned each part.
Uv became popular because it adderesses both sides of that problem. How often developers are willing to recreate, syncronize and validate environments? Most of the times, the answer is none. The importance of uv is therefore not just that it installs packages quickly, it makes the surrounding workflow smaller, since it is broad enough that brings all the different tasks together.


## The Foundation: The pip Era

Python's story with package management began with `pip` in 2008. It was revolutionary for its time: a simple, single command that worked. But `pip` was fundamentally **low-level**—it was a package *installer*, not a *package manager*. So by definition, it is a narrow tool. When you run `pip install requests`, pip does one thing: it downloads the `requests` package and installs it into your active Python environment. It doesn't manage python versions, locking, tool isolation, package tracking or publishing. It just installs, and the rest is handled by other tools.

So developers had to glue together a workflow:

```bash
# 1. Create a virtual environment (separate tool: venv or virtualenv)
python -m venv .venv

# 2. Activate it (shell integration, not pip)
source .venv/bin/activate

# 3. Install packages (pip does this part)
pip install requests

# 4. Lock versions manually (use pip-tools or requirements.txt)
pip freeze > requirements.txt

# 5. Hope to reproduce later...
pip install -r requirements.txt
```

Millions of Python developers are still doing some variation of this. However there are potential dangers: `pip install package-a package-b` might fail if they require incompatible versions of a shared dependency—you'd get an error at install time, not before. `pip freeze` captures *your* environment, but not *why* certain versions were chosen. Two developers running `pip install -r requirements.txt` at different times might get different transitive dependency versions. Deleting a package from `requirements.txt` doesn't remove it from the environment. If you wanted to use `pipx` to install a CLI tool, you'd need to learn a completely different command set.
Pip does it's own resolve about dpendency resolutions, but it may report incompatibilities only after receiving requested constraints and does not provide a porject lockfile workflow by itself. 

The incompleteness of `pip`causes confusion, real enough that developers created memes about it. [XKCD's comic #1987](https://xkcd.com/1987/) perfectly captured the bewilderment of choosing between python, environments, and other overlapping tools. A famously-upvoted [StackOverflow question](https://stackoverflow.com/questions/41573587/) asked: "What is the difference between venv, pyvenv, pyenv, virtualenv, virtualenvwrapper, pipenv, etc?" The fact that this question needed to exist—and be answered in excruciating detail—revealed the ecosystem's core problem: developers were drowning in tools, each solving a slightly different piece of the puzzle.

## The First Attempt: Poetry and Its Constraints

By 2018, `Poetry` emerged with a genuine promise: dependency management and packaging made easy. Poetry offered to replace the entire `pip + venv + pip-tools + twine` stack with a *single opinionated tool*. It introduced a `pyproject.toml` file (later standardized by PEP 621[^13]), automatic virtual environment management hidden from the user, a lockfile (`poetry.lock`) that tracked exact versions and hashes, and built-in packaging and publishing.

You wrote your dependencies in `pyproject.toml`, ran `poetry install`, and it "just worked." The command interface was thoughtful: `poetry add django`, `poetry remove django`, `poetry run python manage.py runserver`. This cohesive tool, was the first widely adopted attempt to declarative metadata (toml file), dependency resolution and locking, virtual management, and build and publish commands.

**1. Slow Dependency Resolution.** Poetry's dependency resolver has a long-standing reputation for being slow on larger projects, and it's one of the most common complaints raised against it.[^21] The practical effect people report is that on big dependency graphs, re-resolving becomes something you avoid doing repeatedly and lean on CI for instead.

**2. Still Needed pyenv for Python Versions.** Poetry didn't manage Python versions. You still needed `pyenv install 3.11 && pyenv local 3.11` before using Poetry.

**3. Still Needed pipx for CLI Tools.** Poetry had `poetry run`, but it required manually syncing with `poetry install` first. For globally-installed tools like `black` or `ruff`, you needed `pipx` (a separate tool with its own commands).

**4. Poetry-Specific Lock File.** `poetry.lock` was Poetry-only. No other tool understood it. Developers who chose Poetry were locked into Poetry's ecosystem. If you later wanted to switch tools or use a different package manager alongside Poetry, you'd have to convert or regenerate your lock file. There was no standard format—just Poetry's proprietary lockfile.[^17]

**5. Opinionated Project Structure.** Poetry enforced strict conventions. For example, when you run `poetry new myproject`, it creates:

```bash
myproject/
├── myproject/          # Your package code
│   └── __init__.py
├── tests/
├── README.md
└── pyproject.toml
```

If you want a different structure—like `src/myproject/` (a common Python best practice), you need to manually configure the `packages` field in `pyproject.toml`:

```toml
[tool.poetry]
packages = [{include = "myproject", from = "src"}]
```

But Poetry's default is flat layout. If you prefer `src/`, you need `poetry new --src` on creation, or manually edit pyproject.toml afterward. Want something else entirely (like a `lib/` folder)? Poetry will fight you. You have to configure it by hand, and if you make a mistake, the build breaks.
Anyway this opinions, later on became more or less standard, so as you can imagine it was not the reason of why it was not globaly adapted. Poetry claimed to unify the toolchain, but it didn't. You still needed `pyenv`, still needed `pipx`, and Poetry's slow resolution meant developers stopped using it locally. It solved dependency management beautifully, but left you managing multiple tools with consistent naming—not actual unification. And that's the reason of why it was not adopted fast enough to capture all the community.

## The Ecosystem Explosion

By the early 2020s, Python's packaging ecosystem had fragmented into overlapping tools, and the situation only grew more complex.[^4] The table below shows how many pieces a developer had to keep straight:

| Tool | Purpose | When You Use It |
|------|---------|-----------------|
| `pip` | Install packages | Always, default choice |
| `virtualenv` / `venv` | Create isolated environments | Before pip install |
| `pip-tools` | Generate lockfiles | If you want reproducibility without Poetry |
| `Poetry` | Dependency manager (with lock files) | If you want structure, but still need pyenv + pipx |
| `pipenv` | Early unified tool | Legacy projects |
| `pyenv` | Manage Python versions | Always needed (even with Poetry) |
| `pipx` | Install CLI tools globally | Always needed (Poetry's `run` requires manual sync) |
| `twine` | Upload packages to PyPI | When publishing packages |
| `setuptools` | Build packages | Runs in background |
| `wheel` | Create binary distributions | Runs in background |

A typical Python project in 2024 looked like this:

```bash
# Install Python version via pyenv
pyenv install 3.11.0
pyenv local 3.11.0

# Create environment via venv
python -m venv .venv
source .venv/bin/activate

# Install dev dependencies via pip
pip install poetry

# Install project dependencies via poetry
poetry install

# But for linting, you'd use pipx (Poetry's tool management is clunky)
pipx install ruff

# And maybe pip-tools for pinning (if you prefer pip over Poetry)
# Publishing? Learn twine or poetry publish (different commands)
```
 Python packaging complexity was distributed across many individually reasonable tools. `uv `made that complexity cheaper to operate by combining the common pieces and making environment operations fast enough to repeat.

## The Hidden Cost: Invisible Friction

<!-- Too repetitive --> 
Python developers adapted and learned in this state. The fragmentation was just "the way it is." But the friction was cumulative—and invisible. You had to remember which tool owned which command, and the answers didn't compose:

```bash
# Which is correct?
pip install numpy          # Traditional
poetry add numpy           # Poetry style
pipx install numpy         # (This doesn't even work; pipx is for tools)
pyenv install 3.11         # (Different tool entirely)
```

And every tool added overhead to CI/CD. Worst of all was the speed-versus-safety tradeoff: when resolution takes 5 minutes, developers stop running it locally and just push to CI to wait.

```bash
# With slow Poetry
$ poetry add new-package
# Waiting... 5 minutes later

# With fast pip (but no lockfile safety)
$ pip install new-package
# (Instant, but might install incompatible versions)
```

Developers picked their "poison". Pip by itself does not provide the same project-level locking workflow that Poetry, thus is 'unsafe' or better said less reproducible resolution. Poetry on the other hand, while providing this mechanim, takes its own time to resolve. Python's packaging wasn't *broken*—it was *tedious*, aka a pile of small annoyances teams eventually becoming numb.

## The Unexpected Solution: uv

This was the state of Python packaging in October 2023. Developers had adapted to the chaos, learned multiple tools, and accepted multi-minute resolution times as normal. But then, Astral released a tool that changed everything, not by adding features, but by making the entire ecosystem suddenly feel optional.

> "When things are way faster, they really change the user's relationship to the tool." — Charlie Marsh, Jane Street Tech Talk[^6]

The clearest example actually comes from Ruff, Astral's linter: linting used to be slow enough that you only ran it in CI, so feedback arrived late. Ruff made it fast enough to run as a pre-commit hook on every save, which is a genuinely different workflow, not just the old one sped up.

That's Ruff's story, though, and it's worth being precise that uv's is not identical. For a package manager, raw speed is the wedge rather than the whole point. Speed is what let uv spread as a no-friction drop-in, and it's what made a few workflow changes practical (more on those below). But the thing that makes uv *stick* is unification, folding pyenv, pipx, pip-tools, venv, and Poetry into one tool. Speed got people to come; consolidation is why we stayed.

> "People didn't think they had a performance problem until they experienced Ruff/uv. Adoption was just so fast." — Charlie Marsh, Talk Python Episode 520[^7]

## Five Pillars: What uv Got Right

uv's success rests on five key insights that previous tools had missed or compromised on:

### 1. Blazing Fast

uv's performance comes from clever caching and a low-level implementation in Rust. Package operations run 10-100x faster than pip, so you can install a hundred dependencies in seconds instead of minutes. That speed helps most where it repeats: CI/CD runs, creating virtual environments, syncing dependencies across a team. Every `uv add` and `uv sync` finishes before you can context-switch away. And speed here isn't cosmetic. It changes how developers work with the tool, which is the thread running through the rest of this post.

### 3. Standards-Based Compatibility

Rather than imposing new conventions, uv worked *with* existing standards. It respects the packaging PEPs already in wide use—PEP 517 (build-system independence), PEP 518 (build system requirements), and PEP 751 (the new standard lock file format)[^14]—along with PEP 621 (project metadata in pyproject.toml)[^13]. Projects could adopt uv without rewriting their `pyproject.toml` or learning a new format, so standards compliance did real work rather than sitting in a marketing bullet. Here UV should thank Poetry, which opened again the world to this.

### 4. Unified Tooling

uv folds what used to need eight separate tools into one command. Python version management, environment creation, dependency resolution, lockfile generation, and tool execution all live in the same place. Developers no longer juggle competing tools or maintain incompatible workflows, and there was nothing to migrate away from because one tool already handled it. And lets not talk about publication on the package to build its own wheels (as you can imagine it has also been pseudo-unified).

### 5. Python Version Management Solved

Before uv, managing Python versions required `pyenv`—a separate tool with its own learning curve and configuration. uv simplified this dramatically. Type `uv python install 3.12` and you're done. No homebrew complications, no pyenv configuration, no manual downloads. Switch between versions with `uv python pin`. The tool automatically downloads missing versions when needed, and `.python-version` files become straightforward to manage. Python version management stopped being a separate concern and became just another thing uv handles.

There's one place uv deliberately doesn't go, and it's the same boundary that kept conda alive: **non-Python system libraries.** uv installs Python packages from PyPI; it doesn't manage compilers, CUDA toolkits, or arbitrary other language binaries (such as C/C++ libraries) the way conda's channels do. For the ML and data-science crowd—conda's old stronghold—the natural question is "but what about GPUs?" The reassuring answer: for the most common workflows, uv is enough. Modern wheels for `torch`, `tensorflow`, `jax`, and `cupy` bundle their CUDA runtime *inside the wheel*, so a single `uv add torch` pulls the GPU build straight from PyPI—you never "install CUDA" separately.

The one real gap is the CUDA *toolkit* (`nvcc`) and other native libraries that still aren't shipped as wheels: if you *compile* custom CUDA kernels, you'll still reach for a system toolkit or the conda-forge world. But that day rarely comes for most developers. We think this shrinking niche—and why the conda-forge world itself is being reinvented around faster, Rust-based tooling like Pixi—deserves its own discussion, so we've spun it out into a companion piece: [conda's long goodbye][conda-successor-post].

## Enabling New Workflows

The uv-specific version of this shows up in how we treat environments. Before, a virtual environment was something you nursed: slow to build, so you protected it and hesitated before blowing it away. With uv, rebuilding a `.venv` from the lockfile is fast enough that we stopped treating it as precious. Our normal habit now is to delete and recreate environments freely rather than debug a mysterious one, because recreating costs seconds. That's not forced on you, though. If you'd rather keep a persistent or system-wide environment, uv can install into the ambient environment instead of a per-project `.venv`. The point isn't that ephemeral environments are mandatory; it's that speed made them a comfortable default where they used to be a hassle.

The linter side adds to this. With Ruff wired into a pre-commit hook, errors get caught before they're pushed instead of in CI. Put together, the day-to-day loop gets tighter, and the same cheap-install property pays off again in CI, where you're more willing to run things you'd previously have cached or skipped.

## The Core Insight

The ecosystem evolved without central planning, which is what tends to happen when a fragmentation problem goes unacknowledged. uv didn't win by adding features. It won by making the rest of the ecosystem feel optional, and it did that by treating **speed as a workflow enabler, not a minor optimization.**

## Adopting uv

The transition to uv requires minimal effort. Installation is a single command:

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

From there, the path depends on where you're starting. Below are the three most common ones.

### Path 1: A Fresh Project

Starting from scratch is the cleanest case—uv handles the Python version, the environment, and dependencies in one flow:

```bash
uv init myproject                # Scaffold a new project + pyproject.toml
cd myproject
uv python pin 3.12               # Pin the Python version (auto-downloads if missing)
uv add requests                  # Add a dependency (creates .venv + uv.lock)
uv run python main.py            # Run inside the managed environment
```

No `pyenv`, no manual `venv`, no separate lockfile tool. One command per intent.

### Path 2: Migrating from pip

Projects using `pip` can switch commands immediately—the mental model barely changes:

```bash
uv add package-name              # Replaces: pip install package-name
uv sync                          # Replaces: pip install -r requirements.txt
uv python install 3.12           # Replaces: pyenv install 3.12
```

If you have an existing `requirements.txt`, you can import it directly:

```bash
uv add -r requirements.txt       # Bring existing pins into pyproject.toml + uv.lock
```

### Path 3: Migrating from Poetry

uv reads the standards-based parts of your existing `pyproject.toml`, so most Poetry projects work with little more than a `sync`:

```bash
uv sync                          # Resolves & installs from your existing pyproject.toml
uv add --dev pytest              # Replaces: poetry add --dev pytest
uv python pin 3.12               # Replaces: pyenv local 3.12
```

The one thing that doesn't carry over is `poetry.lock`—it's Poetry-proprietary, so uv generates its own `uv.lock` on first sync. Commit the new lockfile and you're done.

---

Across all three paths, dependency resolution finishes in seconds rather than minutes, and Python version management comes built in rather than bolted on through a separate tool. Developers no longer have to learn `pyenv`, `pipx`, `pip-tools`, and `Poetry` as four separate, incompatible systems. In practice that pays off in CI/CD, in onboarding, and in the day-to-day pace of development.

You feel it first as faster feedback, with installs finishing before you can context-switch away. Then it shows up as cleaner CI and smoother onboarding.
