Python packaging has never lacked tools instead it has lacked consistently simple workflows. 

Pip installs packaging, but it does not manage project environments, Python versions, lockfiles, or command-line tools. Over time thus, developers combined pip with venv, pyvenv, pip-tools, pipx, Poetry, or Conda. Each tool solved a real problem as it raised the need, but the resulting workflow required developers to remember which tool owned each part.
UV became popular because it addresses both sides of that problem. How often developers are willing to recreate, synchronize and validate environments? Most of the times, the answer is none. The importance of uv is not just that it installs packages quickly, it makes the surrounding workflow smaller, since it is broad enough that brings all the different tasks together.

Here is the question we kept coming back to while writing this: if none of these tools were *broken*, why did a new one spread so fast? Our honest answer is that the pain was never a single bug you could point at. It was the slow tax of remembering which tool owned which step, and we had all quietly agreed to pay it.


## The Foundation: The pip Era

Python’s story with package management began with `pip` in 2008. It provided a simple command for installing packages from PyPI and other indexes, and it became the default installer for many Python projects.[^1]

`pip install` resolves dependencies, builds wheels when necessary, and installs packages into the active Python environment. It supports requirements files, constraints, hash checking, editable installs, and installation from local projects or archives.[^1]

However, pip is primarily an installer. It does not manage Python interpreter versions, project-specific dependency groups, isolated command-line tools, or a complete project workflow. Developers therefore commonly combined it with other tools for those responsibilities.[^1][^2]

A basic requirements-based workflow looks like this:

```bash
# 1. Create a virtual environment (separate tool: venv or virtualenv)
python -m venv .venv

# 2. Activate it (shell integration, not pip)
source .venv/bin/activate

# 3. Install packages (pip does this part)
pip install requests

# 4. Lock versions manually (use pip-tools or requirements.txt)
pip freeze > requirements.txt

# 5. Hope to reproduce later...
pip install -r requirements.txt
```

`pip freeze` records the versions currently installed in one environment. It does not record why those versions were selected, preserve the distinction between direct and transitive dependencies, or guarantee that the result is usable on another platform.[^2]

Tools such as pip-tools addressed some of these limitations. A project could declare direct dependencies in `requirements.in`, compile them into a pinned `requirements.txt`, and install from that compiled file.[^2]

```bash
pip-compile requirements.in -o requirements.txt
pip install -r requirements.txt
```

This improved reproducibility, but the compiled file was generated for the platform on which it was created. Projects supporting multiple platforms could need separate lockfiles.[^2]

Pip also supports experimental generation and installation of PEP 751 `pylock.toml` files, but its documentation notes that generated lockfiles are guaranteed only for the current Python version and platform.[^1]

The incompleteness of `pip`causes confusion, real enough that developers created memes about it. [XKCD's comic #1987](https://xkcd.com/1987/) perfectly captured the bewilderment of choosing between python, environments, and other overlapping tools. A famously-upvoted [StackOverflow question](https://stackoverflow.com/questions/41573587/) asked: "What is the difference between venv, pyvenv, pyenv, virtualenv, virtualenvwrapper, pipenv, etc?" The fact that this question needed to exist and be answered in excruciating detail revealed the ecosystem's core problem: developers were drowning in tools, each solving a slightly different piece of the puzzle.

## The First Attempt: Poetry and Its Constraints

Poetry emerged in 2018 with a focus on dependency management and packaging. It used `pyproject.toml` as a central configuration file for project dependencies and packaging settings, managed virtual environments, resolved dependencies into `poetry.lock`, and provided commands for building and publishing packages.[^3][^4]

`pyproject.toml` did not originate with Poetry. PEP 518 introduced the file for build-system requirements, while PEP 621 later standardized core project metadata in the `[project]` table.[^3][^4]

Poetry reduced the number of tools required for dependency management and packaging. A project could declare dependencies, resolve them, install them, and run commands through a shared interface:

```bash
poetry add django
poetry install
poetry run python manage.py runserver
```

Poetry also provided `poetry.lock`, which recorded resolved package versions and hashes. This gave projects a reproducible dependency set, unlike an unpinned requirements file.[^4]

Several limitations remained:

1. **Interpreter selection.** Poetry did not manage Python interpreter versions. Teams often used `pyenv`, operating-system packages, or another mechanism to install and select Python.

2. **Isolated CLI tools.** Poetry could run project commands, but installing isolated command-line tools such as `ruff` or `black` commonly involved `pipx` or another separate tool.

3. **Tool-specific lockfile.** `poetry.lock` is Poetry-specific. A team moving to another package manager generally generates that tool’s lockfile rather than reusing the existing one.

4. **Project configuration.** Poetry used `[tool.poetry]` configuration alongside project metadata. Some settings were Poetry-specific and did not map directly to later standards-based project configuration.

5. **Resolution performance.** Dependency-resolution performance varies by project and cache state. Astral’s published 2024 comparisons reported faster resolution for uv than Poetry and PDM on selected Jupyter and Transformers workloads.[^5]

Poetry therefore improved dependency management and packaging, but it did not remove every separate concern in a Python project workflow.

## Overlapping Tools and Coordination Costs

By the early 2020s, Python packaging included several tools with overlapping responsibilities. Each addressed a real problem, but projects could combine them in different ways depending on their requirements.[^6]

| Tool | Primary purpose | Typical role |
|---|---|---|
| `pip` | Install and resolve Python packages | Package installation |
| `venv` / `virtualenv` | Create isolated environments | Environment creation |
| `pip-tools` | Compile dependency requirements | Reproducible requirements-based workflows |
| Poetry | Declare, resolve, lock, build, and publish projects | Integrated dependency and packaging workflow |
| `pipenv` | Manage dependencies and environments | Alternative project workflow |
| `pyenv` | Install and select Python versions | Interpreter management |
| `pipx` | Install isolated CLI applications | Command-line tool management |
| `twine` | Upload distributions to a package index | Publishing |
| `setuptools` / `wheel` | Build distributions | Packaging build tools |

These tools were not all required in every project. A requirements-based project might use pip and pip-tools; another might use Poetry; another might use Conda for interpreter and native-library management. The coordination cost depended on which responsibilities the selected tools covered and where developers had to connect them manually.[^6]

For example, a pip-tools workflow could look like this:

```bash
python -m venv .venv
source .venv/bin/activate

pip install pip-tools
pip-compile requirements.in -o requirements.txt
pip install -r requirements.txt
```

A Poetry-based project could instead use:

```bash
poetry add django
poetry install
poetry run python manage.py runserver
```

The two workflows solve overlapping problems through different interfaces. Switching between them requires learning different commands and, in many cases, regenerating lockfiles.

Reproducibility also depended on the workflow. An unpinned `requirements.txt` records requested dependencies but may install different versions at different times. A compiled requirements file or a tool-specific lockfile records resolved versions; however, pip-tools lockfiles generated for one platform may not cover dependencies required on another platform.[^2]

uv later addressed several of these responsibilities through one interface, while retaining compatibility with common pip and pip-tools workflows.[^7][^8]

Python's packaging is thus not *broken*, it is *tedious*, or less metaphorical: a pile of small annoyances are piled and it ends up making the developers team become numb.

## The Unexpected Solution: uv

Astral released uv in February 2024 as a fast package installer and resolver compatible with common pip workflows. In August 2024, it expanded uv to include project management, isolated command-line tools, script execution, and Python installation.[^9]

It is worth pausing on *why* speed mattered here, because it is easy to dismiss as a vanity metric.

> "When things are way faster, they really change the user's relationship to the tool." — Charlie Marsh, Jane Street Tech Talk[^10]

The parallel we felt first-hand is Ruff, Astral's linter: traditional linting was slow enough that you either accepted the wait or pushed it to CI and got feedback late. Ruff made it fast enough to run on every save, which is a genuinely different workflow, not the old one sped up. That said, we should be precise: uv's story is not identical. For a package manager, raw speed is not the whole point. Speed is what got people to try it; consolidation by folding pyenv, pipx, pip-tools, venv, and Poetry into one tool is why we stayed. And on the other hand, Ruff is more opiniated than UV, that's way while both are being more popular, we would say that uv has a faster acceptance growth. 

> "People didn't think they had a performance problem until they experienced Ruff/uv. Adoption was just so fast." — Charlie Marsh, Talk Python Episode 520[^11]

This progression matters for adoption. A requirements-based project could evaluate uv through its pip-compatible interface without immediately moving dependencies into `pyproject.toml` or adopting `uv.lock`. Teams seeking more integration could then adopt uv’s project workflow.

Performance and consolidation address different concerns. Faster resolution and installation reduce the time spent preparing environments. Consolidation reduces the number of tools and manual steps needed to maintain them. uv combines both approaches rather than requiring teams to choose between a familiar installation workflow and a more integrated project interface.[^7][^8]

The following table summarizes areas uv covers. The alternatives are examples, not tools that every project previously needed to use together.

| Concern | Common alternatives | uv interface |
|---|---|---|
| Python installation and selection | `pyenv`, operating-system packages, manual installation | `uv python install`, `uv python pin` |
| Virtual environments | `venv`, `virtualenv` | `uv venv`, or automatic environment management in a uv project |
| Project dependencies | pip with requirements files, pip-tools, Poetry, PDM | `uv add`, `uv remove`, `uv sync` |
| Dependency locking | pip-tools, Poetry, PDM | `uv lock`, `uv.lock` |
| Isolated command-line tools | `pipx` | `uv tool install`, `uvx` |
| Running project commands | Activate an environment, or use a tool-specific runner | `uv run` |
| Building and publishing packages | `build` and `twine`, or Poetry | `uv build`, `uv publish` |

These commands serve different purposes. `uv init` creates a project and `pyproject.toml`; `uv venv` creates an environment. `uv run` executes a command in the project environment after checking that the lockfile and environment are current; it does not run commands in the background.[^8]

## Five Design Characteristics Behind uv’s Appeal

uv combines capabilities that were already available in other Python packaging tools. Its contribution is not that it introduced every capability independently, but that it provides them through a shared interface with an emphasis on performance and compatibility with existing workflows.[^9][^12]

### 1. Faster resolution and installation

uv is implemented in Rust and uses a shared cache to reuse downloaded packages and reduce duplicated work. Astral reports performance improvements of 10–100x over pip in its benchmarks.[^7] These figures describe particular workloads, not a guaranteed improvement for every installation. Results depend on the dependency graph, cache state, network access, and whether packages require compilation.[^7]

The practical relevance is greatest when operations repeat. Local environment recreation, CI installation, and dependency synchronization all contribute to development time. Reducing their duration lowers the cost of keeping environments aligned with a project’s declared dependencies.

Resolution and installation should also be distinguished. Resolution determines which package versions satisfy the requirements. Installation prepares those packages in an environment. A benchmark for one operation should not be presented as a measurement of the entire workflow.

### 2. Incremental adoption

uv provides a pip-compatible interface alongside its project-management interface. A requirements-based project can begin with familiar operations:

```bash
uv venv
uv pip install -r requirements.txt
```

This allows developers to evaluate uv without immediately moving dependencies into `pyproject.toml` or adopting `uv.lock`. Compatibility is not exact: uv documents differences in configuration, package-index handling, and supported command-line options.[^7]

The project interface is a separate adoption step:

```bash
uv add requests
uv sync
```

`uv add` records a project dependency, updates `uv.lock`, and updates the project environment. `uv sync` brings the environment into agreement with the project’s locked dependencies. These commands provide more project-level coordination than `uv pip install`, so they should not be described as interchangeable replacements for pip commands.[^8]

This makes migration incremental: teams can adopt the installer first and the managed project workflow later.

### 3. Standardized metadata, with explicit interoperability limits

uv uses established Python packaging standards. PEP 621 defines project metadata in the `[project]` table of `pyproject.toml`; PEP 518 defines build-system requirements; and PEP 517 defines the interface through which tools invoke a project’s build backend.[^13][^14]

This shared foundation allows uv to work with standard project metadata and build backends. It does not mean that all configuration is interchangeable between tools. Settings such as `[tool.uv.sources]` remain uv-specific, just as other tools have their own configuration sections.[^9] This standards-first posture is itself something practitioners have noticed and written up: senior developers surveying the ecosystem point out that Astral's tools lean on existing PEPs rather than inventing rival formats, which is a large part of why adoption felt safe rather than like lock-in.[^15]

Lockfiles require a similar distinction. uv uses `uv.lock` for its managed project workflow, while PEP 751 defines the standardized `pylock.toml` format. uv can export to `pylock.toml` and install from it through the `uv pip` interface, but the standard format does not represent every capability of uv’s project model.[^16]

Standards reduce migration and integration work without eliminating all tool-specific configuration.

### 4. Coordinated project operations

uv brings dependency declaration, resolution, environment synchronization, and command execution into the same workflow. By default, `uv run` verifies that the project environment is current before executing a command. Developers can therefore run project commands without separately creating, activating, and updating the environment each time.[^8]

The benefit is not only a smaller number of installed tools. It is fewer manually coordinated transitions between recording a dependency, updating resolved versions, installing the result, and selecting the environment in which code runs.

The same interface also covers isolated CLI tools, package builds, and publishing. This broadens uv’s usefulness without requiring every project to use all of its capabilities.[^9]

### 5. Integrated Python version management

The Python interpreter is another project prerequisite that uv can manage. It can install supported Python distributions and download a missing interpreter when needed by commands such as `uv run` or `uv venv`.[^9]

For example:

```bash
uv python install 3.12
uv python pin 3.12
```

The first command installs a matching interpreter. The second records a version preference in `.python-version`, allowing uv to select it for the project. A `3.12` pin selects that release series rather than fixing one exact patch release.[^12]

This reduces the need for a separate interpreter-management step during onboarding. It should not be described as complete environment reproducibility: selecting Python and locking Python dependencies does not capture every operating-system or external runtime requirement.

## Where uv Stops: System Dependencies

uv installs Python packages from package indexes and manages Python project environments. It does not provide a general-purpose package manager for operating-system libraries, compilers, CUDA toolkits, or other native software in the way Conda distributions and channels can.[^17]

This boundary is particularly relevant for machine-learning projects. The appropriate PyTorch build depends on the platform and accelerator: CPU-only, CUDA, ROCm, or Intel GPU builds are distributed through different indexes.[^17]

For example, a plain project dependency such as:

```toml
dependencies = [
  "torch>=2.11.0",
  "torchvision>=0.26.0",
]
```

may install CPU-only wheels on Windows and macOS, while installing a CUDA-enabled Linux build from PyPI, depending on the PyTorch version and platform. Projects that need a particular accelerator or cross-platform behavior must configure the relevant PyTorch index and `tool.uv.sources`.[^17]

For the `uv pip` interface, uv can select a PyTorch index automatically:

```bash
uv pip install torch --torch-backend=auto
```

It can also select an explicit backend:

```bash
uv pip install torch torchvision --torch-backend=cu130
```

At present, `--torch-backend` is available only through the `uv pip` interface, not through `uv add`, `uv lock`, `uv sync`, or `uv run`.[^17]

Running prebuilt GPU wheels may require a compatible NVIDIA driver. Compiling custom CUDA extensions generally requires a CUDA development toolkit and additional build configuration. Teams that need compilers, system libraries, or specialized native dependencies may therefore still use system package managers, Conda-based environments, or container images.[^17][^18]

So the natural question from the ML crowd — conda's old stronghold — is "but what about the NVIDIA drivers and the rest of the GPU stack?" The reassuring answer is that for most workflows uv is already enough: modern `torch`, `tensorflow`, and `jax` wheels bundle their CUDA runtime, so a single `uv add torch` pulls the GPU build straight from PyPI, and you never "install CUDA" as a separate step. Let's be honest — most of the industrial workforce never needs to go lower than that. The one real gap is the CUDA *toolkit* (`nvcc`) and other native pieces that still aren't shipped as wheels; if you compile custom kernels, you'll still reach for a system toolkit or the conda-forge world.

We think this shrinking niche—and why the conda-forge world itself is being reinvented around faster, Rust-based tooling like Pixi—deserves its own discussion, so we've spun it out into a companion piece: [conda's long goodbye][conda-successor-post].

## Adopting uv

Installation is a single command:

```bash
curl -LsSf [https://astral.sh/uv/install.sh](https://astral.sh/uv/install.sh) | sh
```

The appropriate transition path depends on the existing workflow.

### Path 1: A fresh project

```bash
uv init myproject
cd myproject
uv python pin 3.12
uv add requests
uv run python main.py
```

`uv init` creates the project and `pyproject.toml`. `uv python pin` records the preferred Python version. `uv add` records the dependency, creates or updates `uv.lock`, and synchronizes the project environment. `uv run` executes the command in that environment.[^8][^12]

### Path 2: From pip

A requirements-based project can use uv’s pip-compatible interface:

```bash
uv venv
uv pip install -r requirements.txt
```

To adopt uv’s project workflow, import the requirements and synchronize the environment:

```bash
uv init
uv add -r requirements.in -c requirements.txt
uv sync
```

`uv add -r requirements.in` imports direct dependencies. The `-c requirements.txt` constraint preserves the versions already recorded in an existing compiled requirements file when uv creates `uv.lock`.[^8]

For a simple unpinned `requirements.txt`, use:

```bash
uv add -r requirements.txt
uv sync
```

This adopts the project workflow, but uv may resolve newer versions if the requirements file does not pin exact versions.[^8]

### Path 3: From Poetry

uv can read standards-based metadata from an existing `pyproject.toml`. Projects using Poetry-specific configuration may require review and manual changes before synchronization.[^8][^12]

```bash
uv sync
uv add --dev pytest
uv python pin 3.12
```

`poetry.lock` is not migrated. uv generates its own `uv.lock` during project synchronization. Commit the new lockfile once the project configuration has been reviewed.[^8][^12]

## Enabling New Workflows

The uv-specific version of this shows up in how we treat environments. Before, a virtual environment was something you nursed: slow to build, so you protected it and hesitated before blowing it away. With uv, rebuilding a `.venv` from the lockfile is fast enough that we stopped treating it as precious. Our normal habit now is to delete and recreate environments freely rather than debug a mysterious one, because recreating costs seconds. That's not forced on you, though. If you'd rather keep a persistent or system-wide environment, uv can install into the ambient environment instead of a per-project `.venv`. The point isn't that ephemeral environments are mandatory; it's that speed made them a comfortable default where they used to be a hassle.

The linter side adds to this. With Ruff wired into a pre-commit hook, errors get caught before they're pushed instead of in CI. Put together, the day-to-day loop gets tighter, and the same cheap-install property pays off again in CI, where you're more willing to run things you'd previously have cached or skipped.

## The Core Insight

The ecosystem evolved without central planning, which is what tends to happen when a fragmentation problem goes unacknowledged. uv didn't win by adding features. It won by making the rest of the ecosystem feel optional, and it did that by treating **speed as a workflow enabler, not a minor optimization.**

If there is one thing we took away from adopting it ourselves, it is that we had stopped noticing the tax we were paying — the mental context-switch between pyenv, pip, pipx and Poetry — until a single tool made that cost visible by removing it.
